# POC-033 – Excel-/CSV-Importpfad

Stand: 2026-07-26

## Ergebnis

LeonAid kann eine echte Excel-Arbeitsmappe oder eine gleich strukturierte
CSV-/TSV-Datei vor dem Schreiben vollständig analysieren und anschließend
reproduzierbar über den produktiven CRM-Gateway in Twenty importieren.
Mapping, Pflichtfelder, Match-Regeln, Leerzellenverhalten und Reportformat
sind versioniert.

Der Import nutzt Twenty `2.24.0` mit dem in `external-systems.lock` und
`images.env` festgeschriebenen Image-Digest
`sha256:333b6e3d06904293b3bdad9f4a5eb1489fa8719d886b3e6811aff1d0b85b860c`.
Es gibt keine direkten Datenbankzugriffe.

## Gelieferter Vertrag

- Die Golden-Arbeitsmappe enthält eine Anleitung, den initialen Stand
  `Kontakte` und den gezielten Folgestand `Kontakte Update`.
- `infra/twenty/import-mapping.json` beschreibt Spalten, Pflichtfelder,
  unterstützte Record-Typen, Match-Schlüssel und Leerzellenregel.
- Eine stabile UUIDv4 je Quellzeile verbindet Reports über mehrere Läufe.
- Company-Matching normalisiert Unicode, deutsche Umlaute,
  Groß-/Kleinschreibung, Interpunktion und Whitespace.
- Person-Matching verwendet Vor- und Nachname sowie optional die exakt
  gematchte Firma.
- Der Dry Run unterscheidet `new`, `update`, `unchanged`, `conflict` und
  `rejected`, schreibt aber keinen Datensatz.
- Nur eindeutige neue oder geänderte Zeilen werden im Modus `apply`
  geschrieben. Leere Zellen löschen keine Bestandswerte.
- Der Report ist JSON mit Modus `0600`; jede Zeile enthält Excel-/CSV-
  Zeilennummer, Quell-ID, Status, verständliche Begründung, Kandidaten,
  Ziel-ID und Schreibstatus.
- `./leonaid import-crm` bildet denselben Docker- und Gateway-Pfad als
  bedienbaren Projektbefehl ab.

## Reale Vertragsprüfung

Ausgeführt wurde:

```text
./leonaid test-crm-import
```

Der Test:

1. startet Twenty Server, Worker, PostgreSQL und Redis aus leeren isolierten
   Volumes,
2. provisioniert Schema und Least-Privilege-API-Key über die unterstützte
   Metadata API,
3. legt den CRM-Anteil des Golden Dataset über die echte Data API an,
4. liest die echte `.xlsx`-Datei und meldet im Dry Run exakt einen neuen,
   einen zu aktualisierenden, einen konfliktbehafteten und einen verworfenen
   Datensatz,
5. wendet die zwei eindeutigen Änderungen an,
6. verarbeitet das zweite Tabellenblatt und aktualisiert nur Nordsterns
   Postleitzahl und Ort,
7. verarbeitet denselben zweiten Stand erneut, schreibt dabei nichts,
8. beweist über die echte API eine stabile Twenty-ID, genau eine Nordstern-
   und Musterwerk-Firma, zwei weiterhin mehrdeutige Max-Mustermann-Personen
   und keine Person aus der verworfenen Zeile.

Abschlussausgabe:


Der Test verwendet keine Mocks, Fake-Clients, HTTP-Fixtures, direkten
Datenbankzugriffe oder festen Sleeps. Readiness wird ausschließlich über
Compose-Healthchecks mit Deadline bestimmt.
