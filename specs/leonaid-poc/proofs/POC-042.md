# POC-042 – 90-Tage-Sitzung, Widerruf und Fresh Login

Stand: vollständig bewiesen

## Ergebnis

LeonAid besitzt einen eigenen passwortlosen Login per Magic Link oder
sechsstelligem Code. Eine erfolgreiche Anmeldung erzeugt eine serverseitige,
widerrufbare Sitzung mit absolut 90 Tagen Laufzeit. Der Browser erhält nur das
Cookie `__Host-leonaid_session` mit `HttpOnly`, `Secure`, `SameSite=Lax`,
`Path=/` und ohne `Domain`.

Normale Zugriffe aktualisieren den letzten Zugriff, verlängern aber niemals das
absolute Ende. Sensible Admin-Endpunkte verwenden einen zentralen
Fresh-Login-Guard. Die erneute Anmeldung rotiert das geheime Sitzungstoken,
bewahrt Sitzungs-ID und absolutes Ende und macht den alten Wert sofort
wirkungslos. Logout, administrativer Widerruf, Ablauf und Kontosperre werden
bei jedem serverseitigen Zugriff ausgewertet.

Die Rechnungsfreigabe ist noch kein Bestandteil dieses Tasks: POC-042 beweist
den Guard an der realen Einladungsverwaltung. POC-090 muss denselben Guard vor
der dort erstmals vorhandenen echten Rechnungsfreigabe wiederverwenden und in
seinem eigenen E2E-Test erneut belegen.

## Reale Teststrecke

Der gezielte Nachweis läuft vollständig in Docker:

```sh
./leonaid test-sessions
```

Er verwendet keine Mock-Server oder In-Memory-Repositories:

- eine neue PostgreSQL-Datenbank wird bis Migration
  `0004_passwordless_sessions` aufgebaut und mit dem Golden Dataset befüllt,
- FastAPI, der echte Outbox-Worker, Mailpit und Caddy laufen als Container,
- bekannte und unbekannte E-Mail-Adressen erhalten dieselbe öffentliche
  Antwort; nur für das reale Konto entsteht eine verschlüsselte Mail,
- Magic Link und Code werden aus Mailpit gelesen und genau einmal verwendet,
- die Datenbank weist eine exakt 90 Tage gültige Sitzung sowie explizite
  `last_seen_at`-, `fresh_at`-, Ablauf- und Widerrufswerte nach,
- nach Ablauf der beschleunigten Fresh-Frist bleibt normaler Zugriff erlaubt,
  während die echte Einladungserstellung abgelehnt wird,
- der Fresh-Code rotiert das Token innerhalb derselben Sitzung, ohne das
  absolute Ende zu verschieben,
- ein zuvor kopierter Cookie-Wert verliert nach administrativem Widerruf
  sofort seine Wirkung,
- Logout löscht das Browsercookie und widerruft die serverseitige Sitzung,
- ein explizit abgelaufener realer Sitzungsdatensatz wird abgelehnt,
- AuditEvents, Outbox und Containerlogs enthalten weder Codes noch Tokens.

Chromium bedient parallel dazu über `https://localhost:18448` den echten
Login, liest den Code aus der real zugestellten Mail, erhält das sichere
Cookie, arbeitet zunächst normal, wird für die sensible Admin-Aktion zur
frischen Anmeldung geführt und meldet sich anschließend vollständig ab.

Ergebnis:

```text

1 passed
```
