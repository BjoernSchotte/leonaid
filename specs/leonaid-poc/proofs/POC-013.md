# POC-013 – Testkit für echte Systeme

Nachweisdatum: 2026-07-26  
Status: vollständig bewiesen

## Ergebnis

LeonAid besitzt ein gemeinsames Testkit für die realen PoC-Systeme. Die
schmalen Clients unter `packages/testkit/leonaid_testkit/` decken ab:

- LeonAid/FastAPI einschließlich echtem Magic-Link-Login;
- Twenty über die unterstützte REST Data API;
- RustFS über die S3-kompatible API;
- Mailpit über realen SMTP-Versand und dessen HTTP-API;
- Core-PostgreSQL mit explizit read-only ausgeführten Transaktionen.

Jeder Client erhält denselben Diagnosekontext. Fehler nennen dadurch immer
Request-ID, Persona, Charity-Aktion, Golden-Dataset und den fehlgeschlagenen
Prüfschritt. Asynchrone Abhängigkeiten werden mit einer monotonen Deadline
auf einen fachlichen Zielzustand geprüft. Pauschale Wartezeiten liegen nicht
im Testkit.

## Echter Persona-Login

Der Test startet keine vorgefertigte Anna-Sitzung. Er fordert über
`POST /api/v1/auth/login` eine Anmeldung für
`anna.akquise@leonaid.invalid` an, wartet auf die neue Mail in Mailpit,
entnimmt den Magic-Link und schließt ihn über
`POST /api/v1/auth/login/complete` ab.

Das Testkit prüft anschließend:

- Host-only-, Secure-, HttpOnly- und SameSite-Vertrag des Cookies;
- Benutzer-ID und Anzeigename von Anna Akquise über `/identity/me`;
- den Zugriff der realen Sitzung auf die ihr zugeordnete Charity-Aktion.

Die temporäre Sitzung wird nur innerhalb des isolierten Testlaufs in einer
Datei mit Modus `0600` an Chromium übergeben. Sie wird weder ausgegeben noch
versioniert.

## Systemübergreifender Sponsor-Nachweis

Der Golden-Sponsor `Musterwerk GmbH` wird über vier reale Wege gelesen:

| Weg | Bewiesene ID |
| --- | --- |
| PWA „Meine Sponsoren“ | `40000000-0000-4000-8000-000000000001` |
| LeonAid API | `40000000-0000-4000-8000-000000000001` |
| Twenty REST Data API | `40000000-0000-4000-8000-000000000001` |
| Read-only SQL | `40000000-0000-4000-8000-000000000001` |

Die PWA stellt die fachliche Partei-ID als stabiles `data-party-id` am
Sponsoreneintrag bereit. Damit vergleicht der Browsertest nicht nur sichtbaren
Text, sondern die konkrete Twenty-Referenz. `verify_ui.py` führt die vier
Nachweise zusammen und schlägt bei jeder Abweichung fehl.

## Mailpit und RustFS

Der Mailpit-Smoke-Test:

1. merkt sich den aktuellen Nachrichtenbestand;
2. sendet eine echte SMTP-Mail an `poc013-smoke@leonaid.invalid`;
3. wartet über die Mailpit-API auf genau den neuen Empfänger und Betreff;
4. liest die zugestellte Nachricht erneut über die API.

Der RustFS-Smoke-Test schreibt ein eindeutiges Textobjekt mit
SHA-256-Metadatum, liest Inhalt und Metadatum über die S3-API zurück, prüft
beide Hashes und entfernt das temporäre Objekt anschließend.

## Reproduzierbarer Hauptnachweis

```sh
./leonaid test-testkit
```

Der Lauf baut und startet aus leeren projektspezifischen Volumes:
Core-PostgreSQL, Twenty 2.24.0, RustFS, Mailpit, FastAPI, Worker, PWA,
Admin-Web, Public-Web, Caddy und Chromium. Twenty wird über die unterstützten
APIs provisioniert und anschließend mit Golden Data v1 befüllt. Es werden
keine Request-, Datenbank-, CRM-, Storage-, Mail- oder Browser-Mocks
verwendet.

Finales Ergebnis:

```text
testkit-smoke: OK: echter Login, API/Twenty/SQL-Sponsor, SMTP/Mailpit und
RustFS-Hash
1 passed
testkit-ui-proof: OK: UI, LeonAid API, Twenty und read-only SQL
referenzieren denselben Golden-Sponsor
testkit-test: OK: gemeinsame Echt-System-Clients, Magic-Link-Persona,
UI/API/Twenty/SQL-ID, SMTP/Mailpit und RustFS-Hash bewiesen
```
